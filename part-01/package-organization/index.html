    Package organisation¶

    Why even use APM?¶

    Before apm the skills were published per harness. Moreover, the installation was either manual download or via npm. Considering that nowadays repositories with skills can easily reach 100k+ github stars they definitely deserve a customized tool for managing them. This section goes over the reasons why APM is worth using as well as how to define the most frequeltly used primitives. 1

    The irony of GitHub stars distribution

    The irony is that apm has less than 4k stars and remains a niche while skills like grillme go viral. We highly recommend to leave a star for the APM repo and the other resources we mention during the tutorial!

    Benefits¶

    What does an APM package contain?¶

    Let's start with a quick overview of the files, along with a Python analogy. The table below assumes the user knows what uv dependency manager is.

    APM component description Python analogy
    .apm/ dir Stores the raw primitives (skills, agent personas, etc.). src/ dir
    apm.yml The dependencies definition file. pyproject.toml
    apm.lock.yml The exact description of dependencies. uv.lock
    user-name/repo-name Package stored in a GitHub repository. External package stored on PyPi.
    apm_modules/ Stores all transitive dependencies. Lands here when running apm install. Should be gitignored. .venv/lib/python3.x/site-packages
    .agents/, .github/skills etc. Place where primitives are deployed (exact location depends on harness). .venv/lib/python3.x/site-packages

    Add skill¶

    Let's see how to add a skill to .apm/!

    Skills structure¶

    Every skill should follow this directory structure:

    .apm/skills/
+-- your-skill/
    +-- SKILL.md           # required: the skill body
    +-- scripts/           # optional: executable scripts (usually python or bash)
    +-- references/        # optional: context the skill loads on demand (e.g. how fix a often occuring bug)
    +-- assets/            # optional: templates, code listings, images, fixtures to be reused
    +-- examples/          # optional: sample inputs and outputs

    For more details see the author a skill documentation page.

    skill frontmatter¶

    Frontmatter is a header defining the name and description of our skill, loaded at the beginning of each session. Only if the harness/you decide to use it the whole skill body is loaded. Thus the description is important to align with how the skill is intented to be used.

    Example frontmatter¶

    ---
name: top-stacks
description: Use when user wants the best or most relevant Substack posts for a topic, including requests for reading lists or sources that answer specific questions. Return a ranked top five table of directly linked Substack articles with concise one line relevance notes. DO NOT use it for general web research or recommendations not related to Substacks.
---

    Notice that:

    • negative examples are mentioned (less important if you have small number of skills, more important if you have 50+ skills for eliminating conflicts)
    • Use when ... is a good way to start your description.
    • Pay attention to your description, if generated with LLMs it can decrease the user experience.
    • Changing the description is a breaking change.

    Add agent persona¶

    Warning

    Currently APM does not support sub-agents for every harness from the target list. Although Antigravity does support agentic personas. Currently the GitHub issue requesting support for antigravity sub-agents is labelled as deffered.

    What is possible to configure?

    Key Required
    name recommended
    description yes
    model optional
    tools optional
    color optional
    handoffs optional

    Example: 

    ---
name: latex-compiler
description: Compile LaTeX sources with LuaLaTeX, clean generated files, and diagnose latexmk failures without consuming the parent session's context.
model: mai-code-1.1-flash
tools:
  Read: true
  Grep: true
---

    Add a instruction file¶

    This primitive is handled completly diffrently by copilot and claude.

    Key Required Purpose
    description yes One-line summary; used in compiled context indexes
    applyTo yes for instructions Glob (or comma-separated globs) the rule binds to

    Example:

    ---
description: Python style rules enforced on src/ and tests/
applyTo: "**/*.py"
---

- Use `pathlib.Path`, never `os.path`.
- Tests live next to the module under `tests/<module>/`.
- ...

    When using instructions, remember to run apm compile

    Drawbacks of using instrucitons¶

    • Very agressive loading
    • People tend to write very long instructions

    Package layout¶

    You have basically two main choices when designing a package: single skill package or a collection of skills. There are of course more options, but this two are the mostly used. See package types for more detaisl.

    Install a package¶

    Usually I install packages per project using:

    apm install user-name/repo-name

    For skills that I use across projects all the time I install them globally. Thanks to that I avoid setting this up for every project. Usually I pin the packages using the commit hash to avoid drift.

    apm install -g user-name/repo-name

    Maintanance¶

    • Run apm audit to verify divergence between deployed primitives and your lock file.
    • Run apm prune. This command removes installed packages from apm_modules/ that are neither declared in apm.yml nor retained as transitive nodes in apm.lock.yaml. The command also removes their deployed integration files and updates the lockfile.
    • apm self-update. Update apm to latest version. We recommend to update frequently as the tool is activelly developed.
